# v0.1.0 — 初始架构搭建

**日期**: 2026-05-17

## 背景

将散落在桌面的 code-reading、h5-report、sql-exp-replace 三个研发辅助 skill，整合为一个 git 版本化、渐进式加载、可长期迭代的 Claude Code Plugin。`refactor-flow-reward` 因是项目特定的一次性需求脚本，不符合"通用能力"准入标准，不纳入。

参考标杆：
- **anthropics/claude-plugins-official** — auto-discovery 机制、渐进式加载规范、plugin.json 标准
- **CloudAI-X/claude-workflow-v2** — 单插件版本化、README 结构树、CHANGELOG、SemVer
- **jeremylongshore/claude-code-plugins-plus-skills** — 大规模插件生命周期管理、Keep a Changelog、Schema 演进

## 核心架构理念

### Plugin 而非单 Skill

为什么不能把所有 skill 写在一个 SKILL.md 里：单个 SKILL.md 无论触发哪个子能力都会完整加载到 context。20 个 skill 挤在一起就是上千行，token 直接爆炸。

Plugin 的三级渐进式加载解决了这个问题：

| 级别 | 加载内容 | Token 消耗 | 触发条件 |
|------|---------|-----------|---------|
| L1 元数据 | 所有 skill 的 name + description（~50字/个） | 始终在 context | 会话启动 |
| L2 指令体 | 被命中的那个 SKILL.md（<500行） | 命中时加载 | 匹配触发词 |
| L3 资源 | references/、scripts/ | 按需读取 | skill 指令引用 |

### Skill 间调用模型

- 调用方在 SKILL.md 中用自然语言指令声明调用条件
- 运行时通过内置 Skill tool 触发：`Skill("html-report")`
- 被调用方在被触发时才加载 L2/L3，保持渐进式
- 不需要在 plugin.json 中声明依赖关系——Claude Code 从 available_skills 列表中自动发现

例如 code-reading → html-report 的调用链：

```
用户问代码 → code-reading L1 命中 → 加载 L2 指令体
→ 分析完成 → 用户说"整理成报告" → Skill("html-report")
→ html-report L1 命中 → 加载 L2 指令体 → 生成 HTML
```

## 架构决策

### 决策 1: Skill 准入标准

只纳入**通用、可复用**的能力。判据："换个项目、换个语言、换个人，这个 skill 还能用吗？"

| Skill | 判定 | 理由 |
|-------|------|------|
| code-reading | 纳入 | 读代码是任何工程师在任何项目中的高频需求 |
| html-report | 纳入 | 生成报告是跨场景的通用输出能力 |
| sql-exp-replace | 纳入 | SQL 实验号替换是数据开发的高频操作 |
| refactor-flow-reward | 排除 | 针对特定文件的一次性重构，不具备复用价值 |

### 决策 2: 命名规范化

- `h5-report` → `html-report`：中文"HTML5 页面"在英文语境下含义模糊，`html-report` 语义精确
- 目录名、skill name、frontmatter name 三者严格一致
- 插件名使用 kebab-case：`iplugin`

### 决策 3: html-report 的 HTML vs MD 四层决策模型

不每次都问用户要不要 HTML——简单场景直接 MD，复杂场景才问。详见 `skills/html-report/SKILL.md` 的输出阶段章节。

### 决策 4: 双版本号体系

- 插件级 `plugin.json.version` — 反映整体集合变化（新增/删除/改名 skill）
- Skill 级 `SKILL.md frontmatter.version` — 反映单个 skill 的指令迭代
- 两者独立演进，互不绑定

### 决策 5: scripts/ 与 SKILL.md 的分工

- **scripts/**：需要确定性执行或反复重写的代码（Python/Bash 脚本）
- **SKILL.md 指令**：需要 LLM 灵活判断的工作流
- 当前三个 skill 靠自然语言指令即可满足，scripts/ 预留

### 决策 6: CLAUDE.md 用于仓库维护

采用 CloudAI-X 模式在根目录加 CLAUDE.md，但仅在 `/Users/markz/code/tools/iplugin/` 目录下生效，不影响日常在项目目录下的工作。内容涵盖目录约定、准入标准、版本号规则、提交流程。

### 决策 7: 渐进式 CSS 模板

html-report 的 CSS 模板（130+ 行）从 SKILL.md 提取到 `references/css-template.md`。SKILL.md 中只需一行引用指令，Claude 按需读取。SKILL.md 从 274 行瘦身到约 140 行。

### 决策 8: SKILL.md 增加 tags 字段

对标官方 plugin-dev，每个 skill 的 YAML frontmatter 增加 `tags` 字段，便于后续 skill 数量增长时做分类过滤。当前三个 skill 的 tags：
- code-reading: `[code, analysis, tracing]`
- html-report: `[report, html, output]`
- sql-exp-replace: `[sql, data, experiment]`

### 决策 9: versions/ 目录记录每次迭代

每次版本变更在 `versions/` 下记录：内容少写单文件 `vX.Y.Z.md`，内容多建文件夹 `vX.Y.Z/`。记录目标、变更清单、架构决策、排除项及原因。

## 安装架构

采用本地 marketplace + 软链接模式（对标 RDxiaogang）：

```
~/.claude/plugins/marketplaces/iplugin/   ← 市场根目录
├── .claude-plugin/
│   └── marketplace.json                  ← 声明插件名和位置
└── iplugin/ → /Users/markz/code/tools/iplugin  ← 软链接到 git 仓库
```

settings.json 配置：
```json
{
  "extraKnownMarketplaces": {
    "iplugin": {
      "source": { "source": "directory", "path": "~/.claude/plugins/marketplaces/iplugin" }
    }
  },
  "enabledPlugins": { "iplugin@iplugin": true }
}
```

优势：git 仓库是唯一事实源，改 SKILL.md 即生效，无需复制或同步。
