# 带我读代码

## 目标

帮助用户从头到尾、逐步详细地理解一段代码的完整执行链路。重点是按真实代码顺序讲清楚：

```
数据来源 -> 对象创建 -> 初始化/绑定 -> 队列/状态准备 -> 外部触发 -> 分发 -> 具体执行 -> 回调/副作用
```

输出必须是一条连贯叙事链路，让不熟悉这段代码的人也能跟着代码走到最终行为。不要只堆文件片段，也不要用问答式语气堆单点解释。

## 触发边界

### 适用

用户明确表达需要深度导读、完整链路或报告，例如：

- "带我读代码"
- "详细梳理一下这个链路"
- "从入口到触发完整讲一遍"
- "这个逻辑从入口到最终行为是怎么跑完的"
- "生成代码执行链路 HTML 报告"
- "把这个逻辑按代码执行顺序整理出来"

### 不适用

用户只是轻量询问代码含义、让看某个方法或排查一个局部问题时，不使用本技能，直接按普通代码问答处理，例如：

- "看一下这个方法"
- "帮我看看这段代码"
- "这个函数是干嘛的"
- "这里为什么报错"
- "哪里可能有问题"
- "这个变量在哪里赋值"
- "这个方法在哪里调用"
- "这个方法是怎么被调到的"

这些请求通常只需要定位、解释或给出修改建议，不需要完整链路导读。

### 需要确认

用户只说“梳理调用关系”“看看调用链”但没有明确要完整执行链路、深度导读或 HTML 报告时，先按轻量代码问答处理；只有用户补充“完整讲一遍”“带我读代码”“整理成报告”等意图后才使用本技能。

## 工作流程

### 1. 确定阅读边界和主入口

- 先找到用户关心的代码入口文件、类或方法。
- 如果用户给了父容器、组件入口或业务场景，先判断它是否只是"创建者/驱动者"；不要让外围逻辑淹没核心逻辑。
- 明确本次阅读边界：哪些文件是主链路，哪些只是背景。
- 读取主入口完整源码，必要时读取周边 1-2 层调用。
- 如果当前是 EasyBox/xbuild 工程，目标类、包、模块或调用链只能在 Maven/AAR/崩溃栈中看到且 `repos` 没有源码，立即使用 `xbuild-open-source` 反查并自动补开唯一目标仓，再继续阅读；不要停在“源码没拉下来”的提示，也不要求用户重复说“开源码”。

### 2. 先画出代码执行主线

先用一句话确定主线，例如：

```
父容器创建 View -> Manager 分发到真实 View -> View 绑定数据 -> Controller/Manager 生成任务队列 -> 外部进度或状态触发 -> runnable 执行动画
```

后续所有章节都沿这条主线展开。章节顺序必须贴近真实执行顺序，不要按照提问顺序散着讲。

### 3. 追踪数据来源和对象来源

- 找到关键数据结构来自哪里，如 model、config、transition、state、listener。
- 说明数据字段如何转换、默认值如何设置、关键分支依赖哪个字段。
- 找到关键对象在哪里创建：构造函数、inflate、findViewById、new、factory、lazy。
- 对于 View，说明它被添加到哪个父容器，以及父容器是否只负责创建/持有。

### 4. 追踪初始化和绑定阶段

- 找到 init / setData / updateData / bindData 等绑定入口。
- 明确哪些代码只是"准备数据/准备任务/注册回调"，哪些代码才是真正执行行为。
- 遇到队列、Runnable、Animator、Listener 时，必须区分：
  - **创建/入队阶段**：构造对象、设置参数、add 到 queue。
  - **触发/执行阶段**：调用 start、play、run、onStart、onStartAnim 等。

### 5. 追踪触发源和分发路径

- 找到真正触发行为的外部入口，例如播放器进度、状态 observe、点击、生命周期、EventBus、接口回调。
- 如果有多条触发路径，要并列说明它们是否互斥、是否共用状态、是否会重复触发。
- 对每条触发路径按调用栈说明：谁调用谁，传了什么参数，最终落到哪个具体执行方法。

### 6. 追踪动态分发和匿名实现

遇到抽象类、接口、匿名类、lambda、回调时，必须说明"具体实现在哪里"。

尤其是这类代码：

```kotlin
queue.add(object : BaseRunnable(...) {
    override fun onStart() { ... }
})
```

解释时要明确：

- 基类/接口只定义协议，不包含具体逻辑。
- 匿名子类或 lambda 才是具体实现。
- 变量类型可能是基类，但运行时对象是具体子类；调用方法时会动态分发到具体 override。

### 7. 追踪状态变化和防重复机制

- 找到关键状态变量，如 currentIndex、nextStartTime、isShowing、status、visibility。
- 说明状态在哪里初始化、在哪里修改、如何影响后续执行。
- 如果两条路径都可能触发同一行为，要说明靠什么条件保护。

### 8. 输出流程图

- 对复杂链路，优先使用可视化流程图（HTML 中使用内联 SVG、Mermaid 风格图或 PlantUML 风格图）。
- 如果直接输出 Markdown，可以使用 Mermaid 代码块；如果生成 HTML，优先用内联 SVG，避免外部 CDN 依赖。
- ASCII 只用于非常短的链路或用户明确要求；长链路不要使用 ASCII 作为主图。
- 流程图必须按真实执行顺序组织，并标出分叉路径、共用状态和最终执行点。

## 输出格式要求

### 必须包含的内容

1. **阅读边界**：本次重点看哪些文件，哪些外围只作为背景。
2. **执行主线**：用 1-2 句话说明完整链路。
3. **按代码顺序拆解**：每一步都标注：
   - 文件路径（简写）
   - 行号
   - 关键代码片段
   - 这一步在链路中的作用
   - 这是"准备阶段"还是"执行阶段"
4. **对象/数据来源说明**：关键变量、model、helper、listener、runnable、view 是在哪里创建或传入的。
5. **触发机制说明**：谁触发、触发参数是什么、如何分发到最终执行方法。
6. **状态变化说明**：关键状态在哪里改，如何影响后续执行。
7. **完整流程图**：用 Mermaid、PlantUML 风格、内联 SVG 或清晰分层图总结。

### 推荐 Markdown 结构

直接输出 Markdown 时，优先使用以下结构：

```markdown
## 阅读边界
## 执行主线
## 1. 数据来源
## 2. 对象创建
## 3. 初始化/绑定
## 4. 队列/状态准备
## 5. 触发入口
## 6. 分发到具体实现
## 7. 状态变化和副作用
## 完整流程图
## 文件索引
```

### HTML 报告结构

生成 HTML 报告时，使用更适合阅读的章节标题，但顺序仍然必须贴近真实执行顺序。避免"问题 1 / 问题 2"式章节，除非用户明确要求答疑格式。

## HTML 报告要求

当用户要求生成 HTML 时：

- 使用 `html-report` skill 生成单文件 HTML。
- 首屏给出核心结论，但正文必须按代码执行链路组织。
- 报告应面向所有读者，不要出现"你说"、"我们刚才"、"上面的问题"等对话痕迹。
- 用文件 chip、行号、代码块和图示降低阅读成本。
- 时序图/链路图优先用内联 SVG 或 Mermaid/PlantUML 风格图，不要用大段 ASCII。
- 如果使用内联 SVG，节点命名要和代码中的类/方法保持一致，避免画成泛泛的业务流程。

## 输出阶段

分析完成后，判断用户意图决定输出方式：

- 用户要求"生成报告"、"写成HTML" -> 调用 Skill("html-report") 交给它生成 HTML 报告
- 用户只是问代码逻辑 -> 直接在终端输出 Markdown 结论
- 不确定时 -> 主动问一句"需要生成 HTML 报告还是直接输出结论？"

## 注意事项

- 不要假设用户了解代码，每个关键对象都要说明来源。
- 如果某个变量/方法来自父类或其他文件，必须追踪过去看。
- 遇到接口回调，要说明"谁设置的回调"和"什么时候被触发"。
- 遇到 EventBus，要说明"谁发的事件"和"谁收的事件"。
- 遇到匿名类/lambda，要说明具体实现在哪里，不要只指向抽象类或接口。
- 遇到 Runnable/Animator/queue，要区分"创建任务"和"触发任务"。
- 遇到多个触发入口，要说明它们是否共用同一套状态，以及如何避免重复触发。
- 如果发现某条路径实际无效（如 listener 为 null），要明确指出。
