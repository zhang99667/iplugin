# 项目总结写作规范参考

## 语言原则

### 1. 简洁朴素

使用直接、清楚的表达，不追求文采。

推荐：

- "完成 Android 端开发、联调和上线支持"
- "梳理了消息链路和插件上线流程"
- "沉淀了接入文档，降低后续同学接入成本"
- "后续需要继续关注线上效果和异常反馈"

避免：

- "深度赋能业务增长"
- "构建全链路闭环生态"
- "显著夯实组织技术底座"
- "实现业务价值跃迁"

### 2. 不要写成晋升材料

总结面向日常复盘和知识沉淀，不默认拔高个人价值。

避免主动加入：

- "体现了我的架构能力"
- "完成了从执行到规划的转变"
- "具备了全局技术视野"
- "对组织产生长期战略价值"

除非用户明确要求用于晋升、绩效或述职，否则保持工作总结口吻。

### 3. 少堆专业术语

可以保留必要的业务词、模块名和关键字段，但不要把一句话写成术语列表。

推荐：

> 需求涉及 IM 消息结构、智能体下发内容和插件上线流程，组内此前缺少相关接入经验。

避免：

> 需求涉及 IM SDK、MVP、NPS、PMS、长连接、msg ext、send_origin、reply_recommend、recommend_ask 等多维链路协同。

专业术语只在以下情况下保留：

- 用户明确提供，且对说明难点有帮助
- 是项目边界或核心链路的一部分
- 去掉后会影响事实准确性

### 4. 写清楚"做了什么"

总结应说明具体动作，不要只写项目背景。

优先使用：完成 / 梳理 / 对接 / 推动 / 联调 / 验证 / 沉淀 / 优化 / 支持

避免空泛表达：

> 项目完成了能力建设。

应改成：

> 完成 Android 端推荐内容解析、透传和展示支持，并沉淀 IM 接入与插件上线文档。

### 5. 难点要具体

项目难点不要写成泛泛而谈的"链路复杂、协作成本高"。需要说明复杂在哪里。

推荐结构：

```markdown
难点 = 背景差异 + 具体问题 + 处理方式
```

示例：

> 719 场景与现有激励视频架构独立，无法直接复用原有触发链路。通过插件化和事件驱动方式拆出激励逻辑，在尽量不影响现有业务的前提下完成接入。

### 6. 收益要有依据

有明确数据时可以写数据；没有数据时写效率、质量、协作或沉淀收益，不编造量化结果。

推荐：

- "减少后续同类需求的接入沟通成本"
- "为后续排查问题提供链路参考"
- "完成上线验证，当前未发现核心流程回归问题"

避免：

- "显著提升用户留存"
- "大幅提升团队效率 50%"
- "带来长期业务增长"

除非用户明确提供数据和口径，否则不要主动量化。

## 内容取舍规则

### 保留

优先保留以下信息：

1. 工作要解决的问题
2. 用户本人或团队实际完成的内容
3. 真正的技术或协作难点
4. 解决方式和关键决策
5. 明确的业务收益、效率收益或质量收益
6. 文档、工具、流程等可复用沉淀
7. 风险、遗留问题和后续计划

### 删除或压缩

以下内容默认压缩：

1. 过细的字段名
2. 过多模块枚举
3. 代码实现细节
4. 重复表达
5. 不影响理解的背景
6. 没有依据的夸张收益
7. 过强的个人包装

## 标准模板

```markdown
## [项目或需求名称]

**背景与目标：**  
[一句话说明为什么做、要解决什么问题。]

**完成内容：**  
[说明实际完成了哪些工作，包括开发、联调、验证、上线、文档沉淀等。]

**关键难点：**  
[说明最核心的 1～2 个难点，以及采用了什么方式解决。不要展开太长。]

**结果与收益：**  
[说明业务收益、效率收益、质量收益或团队沉淀。没有明确数据时，不要编造数据。]

**经验沉淀：**  
[说明沉淀了什么方法、文档、流程或后续可复用经验。]
```

如果有遗留问题或后续事项：

```markdown
**后续事项：**  
[说明需要继续跟进的风险、数据观察、问题修复或优化方向。]
```

## 简短版要求

当用户说明"简单总结""需求结束后记一下""不要太长""只要几条"时：

- 背景与目标：1 句话
- 完成内容：1～2 句话
- 关键难点：1 句话
- 结果与收益：1 句话
- 经验沉淀或后续事项：1 句话，可选
- 不写长列表
- 不展开技术细节
- 不写宏大总结

## 示例

### 输入

用户提供：

> 私信内支持猜你想问和回复推荐。希望降低用户输入成本。在私信会话界面中，接入智能体下发的猜你想问和回复推荐消息卡片。组内之前没有接触过 IM，我负责安卓端开发和上线，还写了几篇文档。

### 输出

```markdown
## 私信内支持猜你想问和回复推荐（Android）

**背景与目标：**  
在私信会话场景中接入智能体下发的「猜你想问」和「回复推荐」能力，通过推荐问题和推荐回复降低用户输入成本，提升私信互动效率。

**完成内容：**  
完成 Android 端推荐内容在 IM 消息链路中的解析、透传和展示支持，并配合完成联调、上线和基础验证。

**关键难点：**  
组内此前缺少 IM 相关需求经验，IM 架构、消息收发链路、插件开发和上线流程都需要重新熟悉。开发过程中梳理关键链路并沉淀接入、合入和线下签名相关文档，降低后续接入成本。

**结果与收益：**  
需求按计划完成接入，为私信场景提供了更低输入成本的互动能力，同时补齐了组内在 IM 插件接入上的经验沉淀。

**经验沉淀：**  
通过该需求熟悉了私信 IM 的基础链路和插件开发流程，也沉淀了后续同类需求可参考的接入文档。
```

## 修改用户原文时的注意事项

- 不要改变事实。
- 不要编造收益数据。
- 不要把"参与"写成"主导"，除非用户明确说自己主导。
- 不要把"测试阶段"写成"已上线"。
- 如果用户提供了提交号或代码路径，可以用于理解背景，但最终总结不必写提交号。
- 如果材料不足，可以先按现有信息写一版，不要反复追问。
- 如果用户明确说用于晋升、绩效或述职，可以适当保留个人贡献，但仍保持朴素可信。
