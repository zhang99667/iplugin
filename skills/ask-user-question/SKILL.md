# Ask User Question

目标：把真正阻塞后续执行的用户决策交给结构化询问机制，让用户选择后再继续执行。

这个技能不是泛用澄清器。它服务显式调用、规则要求必须询问、风险操作确认和会阻塞执行的选择场景，避免因为普通需求里有一点不确定就频繁打断。

## 触发边界

### 适用

使用本技能处理这些请求：

- 用户通过 `/ask-user-question` 调用。
- 用户明确说“交给 AskUserQuestion”“用 request_user_input 问我”“让我选一下”。
- 用户要求在 UI、交互、实现方案、风险操作存在不确定时先弹选择。
- 仓库或流程规则明确要求“通过 `/ask-user-question` 询问用户”，例如提交前确认是否 `git commit`。
- 后续操作会产生明显外部影响，必须由用户确认方向，例如提交、推送、删除、覆盖、清理、reset、批量写入或执行高风险命令。
- 存在 2 到 3 个互斥方案，且助手无法安全自选；用户选择会直接决定后续文件修改、命令执行或交付内容。

### 不适用

不用于普通闲聊、无需选择的事实回答、已经可以安全直接执行的简单任务，或执行助手自己可以合理判断的低风险取舍。

### 需要确认

如果用户没有显式调用本技能，只是问题本身有多个实现方向，优先继续推进并在普通对话中说明取舍；只有规则要求必须问、选择会阻塞后续文件修改、风险操作需要确认或用户明确要求“让我选”时才使用本技能。

## 工作方式

1. 从用户当前命令参数和最近上下文中提取真正需要用户决策的点。
2. 只问 1 个最关键问题；如果有多个不确定点，选择会阻塞后续工作的那个。
3. 给出 2 到 3 个互斥选项。
4. 推荐项放第一个，并在标签里标注 `(Recommended)`。
5. 每个选项说明一句影响或取舍。
6. 调用当前环境提供的结构化询问工具，例如 `AskUserQuestion` 或 `request_user_input`。
7. 等用户选择后，按选择继续执行原任务；如果用户只想生成问题，则返回选择结果摘要即可。

## 问题设计

问题要短、具体、可选：

- 好：`这个 UI 改动优先走哪种布局？`
- 好：`这个风险操作现在要怎么处理？`
- 差：`你想怎么办？`
- 差：`请详细说明你的所有偏好。`

选项要能直接指导下一步行动：

- `沿用现有布局 (Recommended)`：改动最小，视觉一致性最好。
- `重做为双栏布局`：信息密度更高，但移动端需要额外适配。
- `先只加入口`：风险最低，但体验提升有限。

避免给出“其他”选项；结构化询问 UI 通常会自动提供自由输入。

## 工具不可用时

如果当前环境没有可调用的结构化询问工具，不要假装已经弹窗。退化为普通文本选择题，格式如下：

```markdown
需要你确认一个点：

**问题**：这个 UI 改动优先走哪种布局？

1. **沿用现有布局 (Recommended)**：改动最小，视觉一致性最好。
2. **重做为双栏布局**：信息密度更高，但移动端需要额外适配。
3. **先只加入口**：风险最低，但体验提升有限。
```

退化时明确说明“当前环境没有结构化询问工具可用”，然后等待用户回复。

## 输出约束

- 不要一次问多个问题。
- 不要写长背景说明。
- 不要把选项写成开放式讨论。
- 不要在用户还没选择前继续做会受该选择影响的文件修改或风险操作。
- 如果用户的命令参数已经包含明确选项，直接按该选项继续，不再重复询问。
