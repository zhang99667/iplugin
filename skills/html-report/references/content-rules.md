# HTML 报告内容规则

## HTML vs Markdown 决策

在开始生成之前，按以下逻辑判断输出格式，不需要每次都问用户：

1. 用户明确要求 HTML（说了“生成HTML”“写成HTML报告”“/htmlreport”）时，直接生成 HTML，不询问。默认加入折叠和复制按钮。
2. 用户明确要求终端输出（说了“直接给我”“输出结论”“不用HTML”）时，直接输出 Markdown，不询问。
3. 用户意图模糊（说了“整理一下”“总结一下”等）时：
   - 内容简单（不超过 3 个要点、无代码块、无表格）直接输出 Markdown。
   - 内容复杂（多章节、代码块、表格、多问题）问一句“需要生成 HTML 报告还是直接输出 Markdown？”
4. 被其他 skill 调用时，调用方已经做了判断，直接按调用方指示执行，不重复询问。

## HTML 价值信号

用户没有明确指定格式时，只有内容明显需要 HTML 的可视化表达力，才建议或询问是否生成 HTML。满足以下任一条件时，HTML 通常比 Markdown 更合适：

- 多方案、多个模块、多个问题需要并排比较或扫描。
- 包含代码 diff、调用链、架构图、状态流转、时间线、数据图表或证据矩阵。
- 内容很长，读者需要目录、折叠、锚点或非线性阅读。
- 需要作为交付物分享给评审人、负责人或跨团队读者。
- 需要把结论、证据、风险、行动项放在同一个可浏览页面里。

反过来，只有 1 到 3 个简单结论、没有代码/表格/图示/证据链，或用户明确只要终端结论时，保持 Markdown。

## 内容类型判断

生成 HTML 前先判断它到底是什么文档，不要把所有内容都机械地做成“对话转网页”。

- 正式技术/业务文档：内容有明确交付目的、读者或归档价值，例如技术详设、方案设计、代码评审报告、问题排查报告、需求交付材料、项目总结、复盘、上线计划、接口文档、跨仓库改造说明。这类文档必须加正式抬头。
- 分析报告/工作报告：内容来自当前对话，但已经形成结构化结论，例如评审问题清单、排查结论、实验分析、方案对比、风险评估。通常也应加正式抬头，尤其是包含仓库、卡片号、负责人、排期、版本、分支或日期时。
- 普通对话转 HTML：用户只是要求把聊天内容、上一轮回答、临时说明转成可读页面，没有正式归档语境，也没有项目元信息。使用普通标题和整理时间即可，不强行加大抬头。
- 拿不准时先问用户：“这是要做成正式技术/业务文档，还是只把对话整理成 HTML？”

## 正式抬头要求

正式技术/业务文档、分析报告必须在首屏加入一个“文档抬头”区，类似封面摘要，但不要做成营销 hero。它应该帮助读者在 5 秒内知道：

- 这是什么文档：技术详设、代码评审报告、问题排查报告、需求交付总结、上线方案、对话整理等。
- 主题是什么：用文档标题直接表达核心对象或结论，不要写空泛标题。
- 涉及哪些仓库/模块：优先展示仓库路径、模块名、分支、平台端，如 `baidu/channel/im-android-sdk · master`、`Android 端`。
- 关联任务和上下文：卡片号、需求号、版本、计划上线日期、实验号、项目阶段、状态。
- 责任信息：作者、负责人、评审人或整理人；没有来源时不要编造。
- 时间信息：整理日期、更新时间、评审日期或文档版本。

抬头字段只展示能从内容中可靠提取的信息。缺少关键字段且正式性依赖这些字段时，先问用户补充。

## 输出要求

1. 单文件 `.html`，CSS 和 JS 内嵌在 `<style>` / `<script>` 中，不依赖外部文件、CDN 或运行时高亮库；图表优先使用表格、内联 SVG 或生成期静态内容。
2. 用户没有指定路径时，默认输出到桌面。
3. 文件名表意，例如 `review_report.html`、`rate_limiter_explainer.html`。
4. `/htmlreport` 时直接生成，不再反问，默认带折叠和复制按钮。
5. 判断为正式技术/业务文档或分析报告时，必须加文档抬头；判断为普通对话转 HTML 时不强制加。
6. 完成后只回复文件路径和一句话概要，不复述报告全文。

## 可选依赖与安装

- 默认不安装依赖。`--engine auto` 只探测已有 Pygments 模块或 `pygmentize` CLI，缺失时回退 builtin。
- 只有用户明确要求增强高亮或同意安装时，才说明会写入当前用户 Python 环境并执行安装；安装失败不阻塞报告生成。
- Homebrew Python 触发 PEP 668 时，可在用户确认后使用 `python3 -m pip install --user --break-system-packages Pygments`，避免修改系统包目录。

## 写作规范

- 用户使用中文时，报告默认中文。
- 首屏必须有 TL;DR 或摘要区，让读者不滚动也能知道结论、风险和下一步。
- 每个问题建议包含：优先级、文件路径、行号范围、问题说明、影响、当前代码、修复方案。
- 只要报告涉及代码新增、删除或修改，不能只贴“当前代码”和“修复后代码”。必须明确标出每处变更类型：新增、删除、修改、上下文。
- 修复方案包含代码时，优先展示聚焦 diff；如果用 before/after，也必须在标题或行内标出“修改前/修改后”，并用颜色或标记突出实际变化。
- 多行代码、SQL、XML、JSON、配置片段和 diff 遵循 `references/visual-rules.md` 的代码块规则：用 `scripts/highlight_code.py` 生成，常见语言映射到 `kotlin`、`java`、`js`、`python`、`xml`、`sql`、`json`、`yaml`、`bash`、`diff`、`text`。默认使用 `--engine builtin`，正式报告或复杂语言片段可用 `--engine auto` 尝试本机 Pygments 增强预渲染；Pygments 缺失时不要自动安装，除非用户明确要求；真实 unified diff 使用 `--lang diff --diff-view`。
- 如果代码片段是建议方案而不是已经存在的 git diff，标题写成“建议变更”或“拟修改”，不要伪装成已经发生的提交 diff。
- 行号可能不准确时，说明基于当前本地源码。
- 有绝对路径优先绝对路径，没有则用仓库相对路径。
- 不贴超长完整文件，只放聚焦片段。
- 大段日志、次要章节用 `<details>` 默认折叠，summary 写明折叠了什么；长文档目录例外，必须使用旧版浮动 `<aside class="toc">` 侧栏，默认展开，并通过 `.toc-toggle` 收起/展开整个侧栏。
- 普通对话转 HTML 不用正式抬头，只保留 `<h1>`、整理时间和必要说明。
- 正式技术/业务文档、分析报告和问题排查报告底部必须有“证据来源”区，列出用过的本地文件、命令输出、日志、commit、URL、卡片号或用户提供材料；没有外部证据时写清“基于当前对话/用户提供内容整理”。

## 生成后复查

写完 HTML 后，在回复用户前做一次快速自查并修正明显问题：

1. Judge：确认 HTML 仍然比 Markdown 更适合；如果只是简单结论，不应强行生成复杂页面。
2. Create：确认页面结构匹配内容类型，而不是所有报告套同一个模板。
3. Review：检查标题层级、首屏摘要、证据来源、代码转义、路径 chip、目录锚点、目录默认展开且可整体收起、折叠区、复制按钮、移动端/分屏和打印样式。
4. Improve：发现文字溢出、表格撑破、只靠颜色表达状态、长代码无滚动、链接不可读等问题时，先修 HTML 文件再结束。

## 完成前检查

- 单文件，浏览器可直接打开。
- 标题、总结、问题区与用户任务强相关。
- 已判断内容类型：正式文档/分析报告有文档抬头；普通对话转 HTML 没有强行套正式抬头；拿不准时已询问用户。
- 正式抬头中的文档类型、仓库、任务、负责人、日期、状态等信息都来自用户内容或可靠上下文，没有编造。
- 行内代码用灰色反引号样式，多行代码用接近 IDE 的深绿色背景块和 token 配色或 Pygments inline style，且每个代码块都有复制按钮。
- 已运行 `scripts/check_html_report.py`，不存在外部 CSS/JS 依赖、裸 `<pre><code>`、缺少复制按钮、缺少必要静态高亮结构的代码块，且页面包含 viewport、窄屏、横向滚动和打印样式。
- 涉及代码改动的报告已经提供变更标识：新增行、删除行、修改行、上下文行可区分；没有把旧代码和新代码混在一起。
- 文件路径和行号以单个 `{path}:{line}`、`{path}:{start}-{end}` 或 `{path}:{line}:{column}` chip 展示；有绝对路径时已加 `idea://open` 超链接；没有把路径和行号拆成两个 chip，也没有把行号范围另起一行。
- ASCII 架构图在浏览器中保持缩进、连线和横向滚动，不出现自动换行导致的错位。
- 长内容已折叠，首屏清爽。
- 长文档已加入左侧目录，目录默认展开、可点击按钮整体收起/展开，目录链接能跳转到对应章节。
- 正式报告底部有证据来源区，报告中的事实可追溯。
- 没有不必要的交互元素。
- 回复只说明文件路径和一句话概要。
