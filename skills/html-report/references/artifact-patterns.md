# HTML 报告类型模板

当前沉淀三个高频场景：技术方案、技术调研、问题排查/修复方案。其他类型先使用 `content-rules.md` 和 `visual-rules.md` 的通用规则，不强行套模板。

## 选择规则

- 用户要求“技术方案、详设、架构设计、接口设计、怎么实现、如何落地”时，使用“技术方案模板”。
- 用户要求“技术调研、原理调研、现状梳理、资料综合、可行性分析、最佳实践梳理”时，使用“技术调研模板”。
- 用户要求“问题排查、Bug 分析、根因分析、修复方案、故障复盘、哪里有问题、怎么修”且内容需要整理成交付物时，使用“问题排查/修复方案模板”。
- 如果用户明确要求“选型、A/B 对比、采用哪个方案”，不要套技术调研模板；先按用户意图生成选型/对比报告，或等后续专门沉淀选型模板。
- 多个模板重叠时先判断主目的：要落地实现用技术方案；要理解技术/现状/可行性用技术调研；要说明现象、根因、证据和修复验证用问题排查/修复方案。
- 信息不足时省略缺失字段，不编造负责人、排期、收益、风险等级或数据来源。

## 技术方案模板

技术方案的主线是让读者快速理解“整体怎么做、接口/数据契约是什么、哪些模块要改、每个改动怎么落地、影响什么、怎么验证”。目标/非目标、备选方案和取舍可以作为补充，但不能盖过方案概述和详细改动设计。

推荐页面结构：

1. 文档抬头：标题、文档类型、仓库/模块、任务号、日期等可靠元信息。
2. TL;DR：3 到 5 条，说明方案概述、核心改动、主要影响面、风险和验证方式。
3. 背景与问题：为什么要改，当前链路或现状有什么问题。
4. 方案概述：用一段话和一张图/表说明整体方案，不先陷入细节。
5. 接口与数据结构：先说明接口、协议、字段、配置、缓存、事件、状态、埋点或实验参数变化，作为后续改动的契约基础。
6. 改动总览：用表格快速列出改哪些模块、文件、接口、配置或数据结构。
7. 详细改动设计：逐模块展开说明为什么改、怎么改、边界是什么、和上下游如何配合。
8. 关键流程：展示改动后的调用链、数据流、事件流、状态流转或时序，说明新旧逻辑差异。
9. 影响面与兼容性：影响哪些业务、端、版本、广告位、实验、下游依赖或历史数据。
10. 风险与验证：风险、测试点、回归范围、监控、灰度、回滚或降级策略。
11. 来源与依据：代码路径、历史文档、卡片、日志、命令输出、接口文档或用户提供材料。

可选补充：

- 目标/非目标：只有边界容易误解时再加，例如“本次只改客户端展示，不改服务端策略”。
- 方案取舍：只有存在真实备选方案时再加；不要为了模板硬编 A/B/C。
- 实施计划：只有用户给出阶段、owner、排期或确实需要落地拆解时再加。

HTML 表现建议：

- 首屏使用摘要卡片 + meta chip，不做营销式 hero。
- 方案概述优先用“架构/链路图 + 简短说明”；没有可靠图就用模块关系表。
- 接口与数据结构适合表格或代码块：字段/方法/事件、类型、来源、消费方、兼容策略。
- 改动总览适合表格：模块/文件、改动类型、改动内容、原因、影响。
- 详细改动设计适合分模块卡片，每个卡片包含现状、改法、上下游配合和边界条件。
- 关键流程适合流程图、时序图、调用链、事件流或 before/after 双栏。
- 影响面与风险适合表格或 checklist，状态不能只靠颜色表达。
- 来源与依据放在底部，路径、卡片、URL 保持可点击或可复制。

## 技术调研模板

技术调研报告的主线是让读者理解“这个技术/方案/实现现在是怎么工作的，架构是什么，链路怎么走，数据、事件或状态如何流转，上下游如何协作”。它不是选型报告，不要求候选项、评价标准或对比矩阵，也不默认给落地建议。

推荐页面结构：

1. 文档抬头：标题、文档类型、调研主题、日期、范围等可靠元信息。
2. TL;DR：3 到 5 条关键结论，说明调研对象、核心机制、关键链路和主要限制。
3. 调研对象与范围：这次看哪个技术、模块、方案或链路，不看哪些无关内容。
4. 架构总览：说明整体结构、关键层次、核心组件和职责边界。
5. 核心概念 / 关键对象：解释理解该技术必须知道的对象、术语、状态或协议。
6. 主链路 / 调用链：从入口到出口讲清楚关键调用、分发、回调、异步或生命周期。
7. 数据流 / 事件流 / 状态流：说明数据、事件、状态如何传递和更新，例如 EventBus、Redux、Context、Signals、观察者、消息队列或自定义 dispatcher。
8. 上下游交互：说明上游如何输入、下游如何消费、依赖接口是什么、失败或边界情况如何处理。
9. 关键实现机制：整理源码、框架或方案中的关键设计，例如缓存、调度、并发、渲染、同步、降级、扩展点。
10. 边界条件 / 限制 / 已知问题：说明适用条件、限制、坑点和容易误解的地方。
11. Sources：列出关键来源、访问时间或本地证据；有冲突时说明取舍。

可选补充：

- 未确认点：只有证据不足或结论依赖假设时再加。
- 后续建议：只有用户明确要求“调研后给建议/下一步”时再加。
- 对当前项目的影响：只有调研对象和当前项目强绑定时再加，不作为默认章节。

HTML 表现建议：

- 架构总览适合图、分层列表或组件职责表，优先让读者看懂整体关系。
- 主链路适合流程图、时序图、调用链表或“入口 -> 中转 -> 消费方”的路径图。
- 数据流/事件流/状态流适合专门成图或表，标出来源、载体、转换点、消费方。
- 上下游交互适合接口表或泳道式链路图。
- 关键实现机制用卡片组织，每条机制尽量绑定证据或源码位置。
- 对外部资料或联网结论，Sources 区必须可追溯。
- 未确认点如果存在，单独成区，不要混在最终结论里。
- 如果用户实际要求选型或方案对比，不要强行降级成调研报告。

## 问题排查/修复方案模板

问题排查/修复方案的主线是让读者快速理解“发生了什么、影响什么、根因证据是什么、怎么修、怎么验证不会再出”。它不是完整技术详设，不需要默认铺开接口设计、备选方案或实施计划；除非修复本身涉及新接口、新数据结构或跨模块改造。

推荐页面结构：

1. 文档抬头：标题、文档类型、仓库/模块、任务号、日期等可靠元信息。
2. TL;DR：3 到 5 条，说明问题现象、根因判断、修复策略、风险和验证结论。
3. 问题现象：用户感知、日志表现、错误堆栈、异常指标、复现路径或触发条件。
4. 影响范围：影响的端、版本、模块、业务场景、用户路径、数据范围或回归风险。
5. 根因分析：按真实排查链路说明可疑点、排除项、最终根因；不要只给结论。
6. 证据链：列出关键源码位置、日志、命令输出、截图说明、commit、卡片或用户提供材料。
7. 修复方案：说明最小改法、关键代码变更、边界条件、兼容策略和为什么这样修。
8. 变更明细：用聚焦 diff、before/after 或变更卡片展示新增、删除、修改和上下文。
9. 风险与回归：修复可能影响的链路、需要重点回归的场景、降级或回滚注意点。
10. 验证结果：已跑命令、测试用例、手动验证、未验证原因和待补充验证。
11. Sources：列出本次判断依赖的文件、命令、日志、URL、卡片号或对话材料。

可选补充：

- 时间线：只有问题跨多次操作、发布、灰度或排查节点时再加。
- 复现步骤：只有用户需要手动复现、QA 回归或问题依赖特定操作路径时再加。
- 长日志附录：只放关键日志在正文，完整日志进 `<details>` 或附录。
- 后续治理：只有问题暴露出监控、测试、架构或流程缺口时再加。

HTML 表现建议：

- 首屏用“现象 / 根因 / 修复 / 验证”四格摘要，避免读者先钻进日志。
- 根因分析适合流程图、排查树或“假设 -> 证据 -> 结论”表格。
- 证据链适合表格：来源、位置、观察到什么、支持哪个判断。
- 修复方案和变更明细必须突出变更类型；涉及代码时优先使用聚焦 diff。
- 风险与回归适合 checklist，状态文字必须明确，例如 `已验证`、`待验证`、`需回归`。
- 长堆栈、完整日志、命令原始输出默认折叠，不挤占首屏。
- Sources 放在底部，事实判断必须能追溯到本地文件、命令、日志、URL 或用户材料。

## 降级规则

- 用户只要简短结论时，不使用完整模板，直接输出 Markdown。
- 用户明确要求 HTML 但内容很轻时，使用普通对话转 HTML，不强行加完整技术方案或调研结构。
- 如果技术方案缺少实现上下文，先按已有信息生成“方案草案”，并标出待确认项。
- 如果调研缺少证据来源，不要输出强结论；改为“初步判断”，并列出需要补充验证的来源。
- 如果问题排查缺少日志、源码位置或复现信息，不要伪造根因；改为“初步排查记录”，把已确认事实和待验证假设分开。
