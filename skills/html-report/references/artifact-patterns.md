# HTML 报告内容覆盖参考

本文件沉淀七个高频场景的内容覆盖清单：技术方案、技术调研、问题排查/修复方案、代码评审、验收报告、选型对比、项目总结。它们用来防止漏掉关键内容，不是可直接复制的目录模板。

先按 `content-rules.md` 为当前材料设计叙事主线，再对照最接近的清单补缺。清单项目可以改名、排序、合并或拆分；只有与任务不相关时才省略。不要把项目逐项抄成章节，也不要为了形式完整生成空章节、重复摘要或没有证据的内容。转换已有文档时，原结构已经清晰就优先保留。

## 选择规则

- 用户要求“技术方案、详设、架构设计、接口设计、怎么实现、如何落地”时，对照“技术方案”。
- 用户要求“技术调研、原理调研、现状梳理、资料综合、可行性分析、最佳实践梳理”时，对照“技术调研”。
- 用户要求“问题排查、Bug 分析、根因分析、修复方案、故障复盘、哪里有问题、怎么修”且内容需要整理成交付物时，对照“问题排查/修复方案”。
- 用户要求“代码评审、review、CR、diff review、帮我看这次改动、这段改动有没有问题”且需要形成交付物时，对照“代码评审报告”。
- 用户要求“验收报告、自测报告、测试结果、case 结果、mock 验收、截图/录屏证据、证据矩阵”时，对照“验收报告”。
- 用户要求“选型、方案对比、A/B 对比、采用哪个方案、哪个更合适”时，对照“选型对比报告”。
- 用户要求“项目总结、需求总结、阶段总结、交付总结、复盘、沉淀经验”时，对照“项目总结报告”。
- 多个清单重叠时先判断主目的：要审查代码质量用代码评审；要证明测试结果用验收报告；要做决策用选型对比；要沉淀结果和经验用项目总结；要落地实现用技术方案；要理解技术/现状/可行性用技术调研；要说明现象、根因、证据和修复验证用问题排查/修复方案。
- 信息不足时省略缺失字段，不编造负责人、排期、收益、风险等级或数据来源。

## 技术方案

技术方案的主线是让读者快速理解“整体怎么做、接口/数据契约是什么、哪些模块要改、每个改动怎么落地、影响什么、怎么验证”。目标/非目标、备选方案和取舍可以作为补充，但不能盖过方案概述和详细改动设计。

内容覆盖清单：

- 文档抬头：标题、文档类型、仓库/模块、任务号、日期等可靠元信息。
- 首屏摘要：简要说明方案概述、核心改动、主要影响面、风险和验证方式；形式可以是短文、要点或摘要块。
- 背景与问题：为什么要改，当前链路或现状有什么问题。
- 方案概述：用一段话和一张图/表说明整体方案，不先陷入细节。
- 接口与数据结构：先说明接口、协议、字段、配置、缓存、事件、状态、埋点或实验参数变化，作为后续改动的契约基础。
- 改动总览：用表格快速列出改哪些模块、文件、接口、配置或数据结构。
- 详细改动设计：逐模块展开说明为什么改、怎么改、边界是什么、和上下游如何配合。
- 代码与配置变化：存在真实代码或配置改动时，提供文件定位和聚焦 diff；只有建议代码时明确标成“拟修改”，不伪装成已发生的 diff。
- 关键流程：展示改动后的调用链、数据流、事件流、状态流转或时序，说明新旧逻辑差异。
- 影响面与兼容性：影响哪些业务、端、版本、广告位、实验、下游依赖或历史数据。
- 风险与验证：风险、测试点、回归范围、监控、灰度、回滚或降级策略。
- 来源与依据：代码路径、历史文档、卡片、日志、命令输出、接口文档或用户提供材料。

可选补充：

- 目标/非目标：只有边界容易误解时再加，例如“本次只改客户端展示，不改服务端策略”。
- 方案取舍：只有存在真实备选方案时再加；不要为了模板硬编 A/B/C。
- 实施计划：只有用户给出阶段、owner、排期或确实需要落地拆解时再加。

HTML 表现建议：

- 首屏快速说明方案与范围即可；短文、要点或摘要卡都可以，不固定为卡片布局。
- 方案概述优先用“架构/链路图 + 简短说明”；没有可靠图就用模块关系表。
- 接口与数据结构适合表格或代码块：字段/方法/事件、类型、来源、消费方、兼容策略。
- 改动总览适合表格：模块/文件、改动类型、改动内容、原因、影响。
- 详细改动设计适合分模块卡片，每个卡片包含现状、改法、上下游配合和边界条件。
- 关键流程适合流程图、时序图、调用链、事件流或 before/after 双栏。
- 影响面与风险适合表格或 checklist，状态不能只靠颜色表达。
- 来源与依据放在底部，路径、卡片、URL 保持可点击或可复制。

## 技术调研

技术调研报告的主线是让读者理解“这个技术/方案/实现现在是怎么工作的，架构是什么，链路怎么走，数据、事件或状态如何流转，上下游如何协作”。它不是选型报告，不要求候选项、评价标准或对比矩阵，也不默认给落地建议。

内容覆盖清单：

- 文档抬头：标题、文档类型、调研主题、日期、范围等可靠元信息。
- 阅读入口：说明调研对象、核心机制、关键链路和主要限制；教学型材料也可以给阅读顺序或“必懂”提示。
- 调研对象与范围：这次看哪个技术、模块、方案或链路，不看哪些无关内容。
- 架构总览：说明整体结构、关键层次、核心组件和职责边界。
- 核心概念 / 关键对象：解释理解该技术必须知道的对象、术语、状态或协议。
- 主链路 / 调用链：从入口到出口讲清楚关键调用、分发、回调、异步或生命周期。
- 数据流 / 事件流 / 状态流：说明数据、事件、状态如何传递和更新，例如 EventBus、Redux、Context、Signals、观察者、消息队列或自定义 dispatcher。
- 上下游交互：说明上游如何输入、下游如何消费、依赖接口是什么、失败或边界情况如何处理。
- 关键实现机制：整理源码、框架或方案中的关键设计，例如缓存、调度、并发、渲染、同步、降级、扩展点。
- 实现证据：涉及源码机制时提供关键文件定位和必要的聚焦代码片段；没有代码变化时不要求 diff。
- 边界条件 / 限制 / 已知问题：说明适用条件、限制、坑点和容易误解的地方。
- Sources：列出关键来源、访问时间或本地证据；有冲突时说明取舍。

可选补充：

- 未确认点：只有证据不足或结论依赖假设时再加。
- 后续建议：只有用户明确要求“调研后给建议/下一步”时再加。
- 对当前项目的影响：只有调研对象和当前项目强绑定时再加，不作为默认章节。

HTML 表现建议：

- 架构总览适合图、分层列表或组件职责表，优先让读者看懂整体关系。
- 主链路适合流程图、时序图、调用链表或“入口 -> 中转 -> 消费方”的路径图。
- 数据流/事件流/状态流适合专门成图或表，标出来源、载体、转换点、消费方。
- 上下游交互适合接口表或泳道式链路图。
- 关键实现机制用卡片组织，每条机制尽量绑定证据或源码位置。
- 对外部资料或联网结论，Sources 区必须可追溯。
- 未确认点如果存在，单独成区，不要混在最终结论里。
- 如果用户实际要求选型或方案对比，不要强行降级成调研报告。

## 问题排查/修复方案

问题排查/修复方案的主线是让读者快速理解“发生了什么、影响什么、根因证据是什么、怎么修、怎么验证不会再出”。它不是完整技术详设，不需要默认铺开接口设计、备选方案或实施计划；除非修复本身涉及新接口、新数据结构或跨模块改造。

内容覆盖清单：

- 文档抬头：标题、文档类型、仓库/模块、任务号、日期等可靠元信息。
- 首屏摘要：说明问题现象、根因判断、修复策略、风险和验证结论。
- 问题现象：用户感知、日志表现、错误堆栈、异常指标、复现路径或触发条件。
- 影响范围：影响的端、版本、模块、业务场景、用户路径、数据范围或回归风险。
- 根因分析：按真实排查链路说明可疑点、排除项、最终根因；不要只给结论。
- 证据链：列出关键源码位置、日志、命令输出、截图说明、commit、卡片或用户提供材料。
- 修复方案：说明最小改法、关键代码变更、边界条件、兼容策略和为什么这样修。
- 变更明细：用聚焦 diff、before/after 或变更卡片展示新增、删除、修改和上下文。
- 风险与回归：修复可能影响的链路、需要重点回归的场景、降级或回滚注意点。
- 验证结果：已跑命令、测试用例、手动验证、未验证原因和待补充验证。
- Sources：列出本次判断依赖的文件、命令、日志、URL、卡片号或对话材料。

可选补充：

- 时间线：只有问题跨多次操作、发布、灰度或排查节点时再加。
- 复现步骤：只有用户需要手动复现、QA 回归或问题依赖特定操作路径时再加。
- 长日志附录：只放关键日志在正文，完整日志进 `<details>` 或附录。
- 后续治理：只有问题暴露出监控、测试、架构或流程缺口时再加。

HTML 表现建议：

- 首屏应覆盖“现象 / 根因 / 修复 / 验证”，可用短文、列表或四格摘要，避免读者先钻进日志。
- 根因分析适合流程图、排查树或“假设 -> 证据 -> 结论”表格。
- 证据链适合表格：来源、位置、观察到什么、支持哪个判断。
- 修复方案和变更明细必须突出变更类型；涉及代码时优先使用聚焦 diff。
- 风险与回归适合 checklist，状态文字必须明确，例如 `已验证`、`待验证`、`需回归`。
- 长堆栈、完整日志、命令原始输出默认折叠，不挤占首屏。
- Sources 放在底部，事实判断必须能追溯到本地文件、命令、日志、URL 或用户材料。

## 代码评审报告

代码评审报告的主线是先暴露“会导致缺陷、回归或维护风险的问题”，再给读者足够上下文理解改动。不要把赞美、风格偏好或大段改动摘要放在发现之前。

内容覆盖清单：

- 文档抬头：标题、文档类型、仓库/分支/commit/CR、评审日期等可靠元信息。
- 评审结论：最严重风险、是否建议合入、必须补的验证。
- Findings：按 `P0/P1/P2` 或用户指定优先级排序，每条包含文件定位、问题、影响、证据和建议修复。
- 改动概览：涉及模块、核心文件、行为变化、配置/接口/数据结构变化。
- 关键风险链路：说明哪些用户路径、边界条件、并发/生命周期/兼容性路径最容易受影响。
- 建议修复：给出最小修复方向、可选替代方案和需要避免的副作用。
- 测试缺口：列出缺失的单测、集成测试、手动回归、截图/日志证据或未验证原因。
- Open questions：只放会影响结论的问题，不把普通建议混进去。
- Sources：diff、文件路径、命令输出、日志、CR 链接或用户提供材料。

可选增强：

- 多版本 Review Workspace：只有评审涉及多个文件，且需要在 2 到 3 份完整源码之间判断整文件关系、参考行或差异化标记时加入。放在 Findings / 改动概览之后，真实补丁之前；按 `references/review-workspace.md` 用构建脚本生成。

HTML 表现建议：

- Findings 必须靠前，适合使用严重级别分组卡片或表格；状态文字不能只靠颜色。
- 文件定位使用可点击路径和行号；不要把行号拆成单独不可跳转 badge。
- 真实 unified diff 必须使用 `highlight_code.py --lang diff --diff-view` 生成聚焦 diff；不要展示整文件。
- 用户明确要求完整多版本审阅，或聚焦 diff 无法表达整文件关系时，使用 Review Workspace；Workspace 不能替代 Findings 和标准 diff viewer。
- 长 diff、长日志和重复证据默认折叠；每个问题正文只放能支撑判断的最小证据。
- 如果没有发现问题，明确写“未发现阻塞问题”，并说明残余风险和未覆盖验证。

## 验收报告

验收报告的主线是证明“测了什么、怎么测的、结果是什么、证据在哪里、还剩什么风险”。它要让后续接手的人能复核结果，而不是只看到结论。

内容覆盖清单：

- 文档抬头：标题、文档类型、需求/任务/版本、环境、日期等可靠元信息。
- 验收结论：总体结论、通过/失败/阻塞数量、关键缺陷、发布或继续回归建议。
- 验收范围：本次覆盖的端、版本、入口、实验、账号、设备、接口、数据和排除项。
- 环境与前置条件：设备、构建产物、mockserver、配置、账号、网络或开关状态。
- Case 矩阵：case id、场景、步骤/输入、预期、实际、结果、证据链接、备注。
- 逐 case 证据：每个关键 case 展示截图、录屏、关键帧、日志、接口命中或数据核验。
- 缺陷与回归风险：失败 case、疑似问题、影响面、当前处理状态和阻塞程度。
- 验证命令与原始证据：adb、curl、日志、SQL、脚本输出等关键证据，长内容折叠。
- 待补充项：未测原因、依赖条件、下一轮验证安排或需要用户确认的事项。
- Sources：测试用例、scheme、mock 配置、日志、媒体文件、用户提供材料。

HTML 表现建议：

- 首屏用结论摘要 + case 统计；不能只靠绿色/红色表达结果。
- Case 矩阵适合表格，证据列链接到同页证据卡或本地媒体文件。
- 图片/视频按 `visual-rules.md` 的媒体证据规则展示；视频必须带 controls，截图必须有 alt。
- 日志和命令输出只展示关键段落，完整输出放 `<details>`。
- Android mock 验收这类强证据场景，应优先呈现 case、截图/录屏占位、mock 命中和证据矩阵。

## 选型对比报告

选型对比报告的主线是回答“要在几个候选项里选哪个，为什么，代价是什么”。它不是普通调研报告，必须把决策标准和取舍讲清楚。

内容覆盖清单：

- 文档抬头：标题、文档类型、决策主题、范围、日期等可靠元信息。
- 推荐结论：推荐方案、核心理由、主要代价、需要补充验证的点。
- 决策问题与约束：要解决什么问题，必须满足哪些业务、技术、成本或时间约束。
- 候选方案：每个候选项的基本做法、适用场景、前置条件。
- 评价标准：性能、稳定性、维护成本、接入成本、兼容性、可观测性、团队熟悉度等真实标准。
- 对比矩阵：逐标准比较候选方案；没有可靠权重时不要虚构分数。
- 推荐与取舍：说明为什么推荐、放弃什么、短期和长期代价是什么。
- 风险与验证计划：需要原型、压测、灰度、试点或回滚验证的项目。
- Sources：调研材料、源码、文档、数据、实验结果或用户提供材料。

HTML 表现建议：

- 对比矩阵放在推荐之后或之前都可以，但首屏必须给出推荐结论。
- 评分只在用户提供权重或有可靠数据时使用；否则用“强/中/弱、支持/不支持、已验证/待验证”等可解释状态。
- 对关键取舍使用短卡片，避免把结论埋进长表格。

## 项目总结报告

项目总结报告的主线是沉淀“目标是什么、交付了什么、结果如何、踩了哪些坑、后续怎么做”。它面向复盘和交接，不要写成宣传稿。

内容覆盖清单：

- 文档抬头：标题、文档类型、项目/需求、周期、参与方、日期等可靠元信息。
- 项目摘要：目标达成情况、核心交付、关键结果、遗留风险和后续动作。
- 背景与目标：为什么做，成功标准是什么，哪些目标不在本次范围。
- 交付范围：功能、文档、脚本、配置、实验、上线项或修复项。
- 时间线与里程碑：关键节点、决策、变更和交付状态。
- 结果与证据：可靠指标、验收结论、用户反馈、上线状态或验证结果。
- 关键决策与取舍：为什么这样做，放弃了什么，保护了哪些约束。
- 问题与经验：风险、踩坑、流程缺口、技术债和可复用经验。
- 后续行动：owner、事项、优先级、依赖和状态；缺 owner 时不要编造。
- Sources：卡片、PR、报告、日志、验收材料、数据来源或用户材料。

HTML 表现建议：

- 用时间线表格或里程碑列表展示过程，不要把所有内容堆成流水账。
- 结果必须绑定证据；没有可靠指标时写“未提供量化指标”，不要臆造收益。
- 后续行动适合 checklist 或任务表，明确状态和依赖。

## 降级规则

- 用户只要简短结论时，不展开完整清单，直接输出 Markdown。
- 用户明确要求 HTML 但内容很轻时，使用普通对话转 HTML，不强行加完整技术方案或调研结构。
- 如果技术方案缺少实现上下文，先按已有信息生成“方案草案”，并标出待确认项。
- 如果调研缺少证据来源，不要输出强结论；改为“初步判断”，并列出需要补充验证的来源。
- 如果问题排查缺少日志、源码位置或复现信息，不要伪造根因；改为“初步排查记录”，把已确认事实和待验证假设分开。
- 如果代码评审缺少 diff 或文件上下文，改为“评审记录草案”，只基于已知改动说明风险。
- 如果验收报告缺少媒体、日志或 case 结果，不要写成已通过；标记为“待补证据”或“未验证”。
- 如果选型对比缺少候选项或标准，先列出决策问题和待补标准，不虚构评分。
- 如果项目总结缺少指标或时间线，保留可靠事实并标明“未提供量化结果”。
