# HTML 报告

当用户希望把分析结论、代码评审意见、问题清单、修复方案、技术方案或排查结果整理成一个独立 HTML 文件时，使用这个技能。默认生成一个可以直接在浏览器打开的 `.html` 文件，通常放到桌面。

## 输出阶段：HTML vs Markdown 决策

在开始生成之前，按以下四层逻辑判断输出格式，**不需要每次都问用户**：

1. **用户明确要求 HTML**（说了"生成HTML"/"写成HTML报告"/"/htmlreport"）→ 直接生成 HTML，不询问
2. **用户明确要求终端输出**（说了"直接给我"/"输出结论"/"不用HTML"）→ 直接输出 Markdown，不询问
3. **用户意图模糊**（说了"整理一下"/"总结一下"等）：
   - 内容简单（≤3 个要点，无代码块，无表格）→ 直接输出 Markdown，不询问
   - 内容复杂（多章节、代码块、表格、多问题）→ 问一句"需要生成 HTML 报告还是直接输出 Markdown？"
4. **被其他 skill 调用时** → 调用方已经做了判断，直接按调用方的指示执行，不重复询问

## 核心目标

生成的是"工程报告页面"，不是普通文本堆砌。重点是让问题、证据、代码和修复方案一眼可扫：

- 页面背景使用柔和浅灰色，主体内容居中展示。
- 每个总结区、问题区使用白色圆角卡片和轻微阴影。
- 优先级、状态、分类使用彩色胶囊标签。
- 文件路径和行号使用 chip 样式，便于快速定位。
- 行内代码标识使用类似 Markdown 反引号的灰色小代码块，比如 `WebPanelAction.kt`、`sdk_script`、`notifyReceivedTitle()`。
- 多行代码片段使用深色高对比代码块。
- 中文说明要简洁、准确，突出问题、影响和修复方案。

## 触发场景

用户出现以下意图时使用这个风格：

- "整理成 HTML 放到桌面"
- "把这些问题整理成 HTML 报告"
- "生成一个代码 review HTML"
- "把结论、代码、行数、说明整理成页面"
- "写成 HTML 报告"
- "后面每次让你整理成HTML"
- "/htmlreport"：把当前回答、上一轮回答或最近整理出的结论直接转换成 HTML 报告并输出到桌面

如果用户明确要求其他视觉风格，以用户的新要求为准。

## 输出要求

1. 生成一个单文件、可独立打开的 `.html`。
2. CSS 写在 HTML 内部的 `<style>` 标签中，不依赖外部 CSS 或 JS。
3. 用户没有指定路径时，默认输出到桌面。
4. 文件名要能表达内容，例如：
   - `review_report.html`
   - `webpanel_cv_fix_report.html`
   - `code_review_fix_report.html`
5. 如果用户输入 `/htmlreport`，默认把当前回答、上一轮回答或最近一次已整理出的内容作为报告正文，不再反问，直接生成 HTML。
6. 完成后只需简短回复文件路径和主要内容。

## 视觉样式和 HTML 骨架

读取 `references/css-template.md` 获取完整的 CSS 模板和 HTML 骨架结构。生成报告时使用其中的样式和结构。

## 写作规范

- 用户使用中文时，报告默认使用中文。
- 内容简洁但完整，优先服务代码评审和问题定位。
- 每个问题建议包含：优先级、文件路径、行号范围、问题说明、影响、当前代码、修复方案。
- 行内的文件名、类名、方法名、参数名、常量名、短代码片段都用 `<code>...</code>` 包起来，形成类似 Markdown 反引号的灰色小代码块，避免和正文混在一起。
- 多行代码片段或命令才使用 `<pre><code>...</code></pre>`。
- 如果行号可能不准确，要说明行号基于当前本地源码，评审系统里应结合上下文定位。
- 有绝对路径时优先使用绝对路径；没有则使用仓库相对路径。
- 代码块内注意转义 HTML 特殊字符：`&lt;`、`&gt;`、`&amp;`。
- 不要贴超长完整文件，只放和问题相关的聚焦片段。
- 使用 `.p0`、`.p1`、`.p2` 表达优先级；如果不是问题等级场景，也可以把它们作为分类标签使用。

## 完成前检查

生成报告后确认：

- HTML 是单文件，可以直接在浏览器打开。
- 标题、总结、问题区都和用户任务强相关。
- 行内代码标识已经用灰色反引号样式区分。
- 多行代码块使用深色背景，长度适中。
- 文件路径和行号以 chip 形式展示。
- 最终回复只需简要说明输出文件路径和内容。
