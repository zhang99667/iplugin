# HTML 报告

当用户希望把分析结论、代码评审意见、问题清单、修复方案、技术方案或排查结果整理成一个独立 HTML 文件时，使用这个技能。默认生成一个可直接在浏览器打开的 `.html` 文件，通常放到桌面。

## 核心理念：用 HTML 做更好的可视化

HTML 相比 Markdown 的核心优势不是"能加 JS 交互"，而是**可视化表达力**：

- **卡片和网格**：用卡片承载每个问题/结论，网格排列多方案对比，远比 Markdown 平铺文本层次分明。
- **颜色即信息**：优先级标签（红/橙/蓝）、状态标记（绿/黄）、文件 chip 色块，不需要读文字就能感知严重程度。
- **图表与架构图**：流程图、架构图、时间线按内容选择 SVG、表格或 ASCII；如果使用 ASCII，必须保持缩进、连线和横向滚动，确保浏览器里完整可读。
- **表格天生好用**：表头对齐、列宽自适应，不用手动对齐 Markdown 的 `|` 分隔符。
- **排版余白**：字号层级、卡片间距、折叠收纳，让信息层级一目了然。

交互只是辅助，**永远不要因为能做就加**。一个只有折叠+复制按钮的干净报告，远好过一个布满滑块和拖拽的花哨页面。

## 输出阶段：HTML vs Markdown 决策

在开始生成之前，按以下逻辑判断输出格式，**不需要每次都问用户**：

1. **用户明确要求 HTML**（说了"生成HTML"/"写成HTML报告"/"/htmlreport"）→ 直接生成 HTML，不询问。默认加入折叠和复制按钮。
2. **用户明确要求终端输出**（说了"直接给我"/"输出结论"/"不用HTML"）→ 直接输出 Markdown，不询问。
3. **用户意图模糊**（说了"整理一下"/"总结一下"等）：
   - 内容简单（≤3 个要点，无代码块，无表格）→ 直接输出 Markdown，不询问
   - 内容复杂（多章节、代码块、表格、多问题）→ 问一句"需要生成 HTML 报告还是直接输出 Markdown？"
4. **被其他 skill 调用时** → 调用方已经做了判断，直接按调用方的指示执行，不重复询问

## 内容类型判断与正式抬头

生成 HTML 前先判断它到底是什么文档，不要把所有内容都机械地做成“对话转网页”。

### 先判断文档类型

- **正式技术/业务文档**：内容有明确交付目的、读者或归档价值，例如技术详设、方案设计、代码评审报告、问题排查报告、需求交付材料、项目总结、复盘、上线计划、接口文档、跨仓库改造说明。这类文档必须加正式抬头。
- **分析报告/工作报告**：内容来自当前对话，但已经形成结构化结论，例如评审问题清单、排查结论、实验分析、方案对比、风险评估。通常也应加正式抬头，尤其是包含仓库、卡片号、负责人、排期、版本、分支或日期时。
- **普通对话转 HTML**：用户只是要求把聊天内容、上一轮回答、临时说明转成可读页面，没有正式归档语境，也没有项目元信息。使用普通标题和整理时间即可，不强行加大抬头。
- **拿不准时先问用户**：如果无法判断是正式文档还是普通对话转 HTML，问一句：“这是要做成正式技术/业务文档，还是只把对话整理成 HTML？”不要擅自套正式抬头。

### 正式抬头要求

正式技术/业务文档、分析报告必须在首屏加入一个“文档抬头”区，类似封面摘要，但不要做成营销 hero。它应该帮助读者在 5 秒内知道：

- **这是什么文档**：技术详设、代码评审报告、问题排查报告、需求交付总结、上线方案、对话整理等。
- **主题是什么**：用文档标题直接表达核心对象或结论，不要写空泛标题。
- **涉及哪些仓库/模块**：优先展示仓库路径、模块名、分支、平台端，如 `baidu/channel/im-android-sdk · master`、`Android 端`。
- **关联任务和上下文**：卡片号、需求号、版本、计划上线日期、实验号、项目阶段、状态。
- **责任信息**：作者、负责人、评审人或整理人；没有来源时不要编造。
- **时间信息**：整理日期、更新时间、评审日期或文档版本。

抬头字段只展示能从内容中可靠提取的信息。不要编造仓库、负责人、日期、卡片号或上线计划；缺少关键字段且正式性依赖这些字段时，先问用户补充。

### 抬头视觉规范

- 抬头位于正文最前面，比普通 `.summary` 更醒目，但仍然是工程文档风格。
- 推荐使用横向渐变或深色底的 `doc-header`，圆角不超过 16px，内部包含标题、简短说明和 meta chip。
- meta chip 可以包含文档类型、任务号、仓库、分支、负责人、日期、状态、平台端、版本等；不要塞太多，优先 4-8 个。
- 如果文档涉及多个仓库，用多个 chip 或一个“涉及仓库”列表；不要把长路径挤进标题。
- 普通对话转 HTML 不用正式抬头，只保留 `<h1>`、整理时间和必要说明。

## 设计原则

1. **可视优先，不是美观优先**：最高优先级是让读者快速看懂结构、链路、差异和结论；装饰感让位于信息可读性。
2. **整洁**：视觉元素服务于信息分层，不堆颜色、不堆动画、不把报告做成海报。
3. **克制**：加任何交互前先问自己——没有它读者会看不明白吗？如果不会，就不加。
4. **首屏即答案**：打开页面不需要滚动、不需要点击就能看到核心结论。详情和证据再往下排。
5. **一页一事**：每个卡片/区块只讲一件事。宁可多几张卡片，不要一张卡片塞五件事。

## 核心视觉标准

延续用户认可的报告风格：

- 页面背景柔和浅灰（`#f6f8fb`），主体内容居中，最大宽度 1180px。
- 总结区和问题区使用白色圆角卡片（14px），轻微阴影。
- 优先级、状态用彩色胶囊标签（P0 红 / P1 橙 / P2 蓝）。
- 文件路径和行号用 chip 样式（缩进色块 + 等宽字体）。
- 行内代码用灰色小反引号样式（`<code>` 标签，`#f1f5f9` 底 + `#334155` 字色）。
- 多行代码用深色背景块（`#111827`），旁边放 copy 按钮，并对关键字、字符串、数字、注释等做颜色区分。
- 长日志、次要章节用 `<details><summary>` 默认折叠。
- 长文档使用左侧目录固定导航，快速跳转到各章节。
- 中文说明简洁准确，突出问题、影响和修复方案。

## 长文档目录导航

当报告内容较长时，需要在左侧加入目录，方便读者随时切换章节，避免反复滚动查找。

满足任一条件就视为长文档：

- 一级/二级章节超过 5 个。
- 内容包含多组问题、方案、链路、日志或验证结果。
- 预期阅读需要多次上下滚动定位。

生成长文档时：

- 使用固定在左侧的 `<aside class="toc">` 展示目录，正文放入 `<main class="content">`。
- 目录项对应正文主要 `<h2>` 章节，每个章节设置稳定的 `id`，目录用锚点跳转。
- 当前不需要复杂 JS 高亮；保持目录常驻、简洁、可点击即可。
- 小屏幕下目录改为顶部普通卡片，不遮挡正文。
- 短报告不要强行加目录，避免页面显得笨重。

## ASCII 架构图与代码块

### 代码高亮要求

代码块不能只是深色背景加纯文本。报告中的多行代码必须具备可见的高亮层次：

- 优先用 `<span class="tok-key">`、`tok-str`、`tok-num`、`tok-cmt`、`tok-fn`、`tok-var` 等 class 标出关键字、字符串、数字、注释、函数名和变量名。
- 不需要完整编译级语法分析，但至少要让读者一眼区分注释、字符串、关键逻辑和普通标识符。
- 差异代码可额外使用 `tok-add` / `tok-del` 标识新增和删除行。
- 短代码块也要高亮核心 token；如果片段极短，至少高亮关键字或注释。
- 代码内容必须先转义 HTML，再包高亮 span，避免 `<`、`>`、`&` 破坏页面。

- ASCII/树状架构图必须保持原始换行、缩进和连接符，不要让浏览器自动换行破坏结构。
- ASCII 图使用专用浅色容器，例如 `<pre class="ascii-diagram">...</pre>`；样式必须包含等宽字体、`white-space: pre`、`overflow-x: auto`、合适行高和横向滚动。
- 复杂架构图可以按“入口链路 / 分支类型 / 归因参数链路”等小标题拆成多个 ASCII 块，但不要为了美观改写节点含义。
- 多行代码块必须放在 `.code-wrap` 容器中，使用 `<pre><code class="language-xxx">...</code></pre>`，右上角提供复制按钮。
- 代码块要有可读的颜色区分；没有引入语法高亮库时，也要手工给关键 token 包 `<span>` 使用模板里的高亮 class。

## 可用交互（按实用程度排序）

### 几乎所有报告都该有的

- **折叠**：`<details><summary>`，零 JS，原生支持。折叠堆栈日志、大段 diff、次要分析。关键是 summary 要写清楚"点击展开什么"。
- **复制按钮**：代码块右上角一个低调的小按钮，hover 才显示。点击复制后反馈"已复制"1.5 秒。实现见 CSS 模板。

### 视情况用的

- **左侧目录**：当报告较长、章节超过 5 个或需要频繁跨章节查阅时使用。目录固定在左侧，点击跳转到正文章节。
- **标签页**：当报告天然有 2-3 个并列视角时用（如"问题/修复/验证"、"方案 A/B/C"）。用纯 CSS 实现，不引入 JS。视角只有一个时不需要。
- **可排序表格**：5 行以上数据表才加表头点击排序。3-4 行的迷你表不需要。

### 大多数时候不需要的

以下能力仅当用户明确要求对应场景时才加入，不要在普通报告中自行发挥：

- 滑块/开关调参（仅设计原型场景）
- 拖拽排序（仅 ticket 排序场景）
- 实时预览编辑器（仅 prompt 调试场景）
- 表单编辑器（仅配置管理场景）

## 输出要求

1. 单文件 `.html`，CSS 和 JS 内嵌在 `<style>` / `<script>` 中，不依赖外部文件（CDN 图表库除外）。
2. 用户没有指定路径时，默认输出到桌面。
3. 文件名表意，例如 `review_report.html`、`rate_limiter_explainer.html`。
4. `/htmlreport` 时直接生成，不再反问，默认带折叠和复制按钮。
5. 判断为正式技术/业务文档或分析报告时，必须加文档抬头；判断为普通对话转 HTML 时不强制加。
6. 完成后只回复文件路径和一句话概要，**不要**复述报告全文。

## 使用场景速查

| 场景            | 关键可视化手段                       | 可选交互                        |
| ------------- | ----------------------------- | --------------------------- |
| **代码评审报告**    | 优先级标签、文件 chip、代码 diff 深色块     | 折叠（长 diff）、复制按钮             |
| **问题排查/修复方案** | 问题卡片、根因流程图(SVG)、修复 check-list | 折叠（堆栈）、标签页（问题/修复/验证）        |

## 写作规范

- 用户使用中文时，报告默认中文。
- 每个问题建议包含：优先级、文件路径、行号范围、问题说明、影响、当前代码、修复方案。
- 行内代码标识用 `<code>...</code>` 包起来。
- 多行代码用 `<pre><code class="language-xxx">...</code></pre>`，放在 `.code-wrap` 容器中并加复制按钮；代码块必须有深色背景和可读的语法高亮层级，关键 token 要包高亮 span。
- 行号可能不准确时，说明基于当前本地源码。
- 有绝对路径优先绝对路径，没有则用仓库相对路径。
- 代码块内转义：`&lt;`、`&gt;`、`&amp;`。
- 不贴超长完整文件，只放聚焦片段。
- 大段日志、次要章节用 `<details>` 默认折叠，summary 写明折叠了什么。

## 完成前检查

- 单文件，浏览器可直接打开。
- 标题、总结、问题区与用户任务强相关。
- 已判断内容类型：正式文档/分析报告有文档抬头；普通对话转 HTML 没有强行套正式抬头；拿不准时已询问用户。
- 正式抬头中的文档类型、仓库、任务、负责人、日期、状态等信息都来自用户内容或可靠上下文，没有编造。
- 行内代码用灰色反引号样式，多行代码用深色背景块，且每个代码块都有复制按钮。
- 代码块有可见语法高亮，不是纯色纯文本；关键字、字符串、数字、注释等至少有基础颜色区分。
- 代码块有复制按钮，hover 可见。
- 文件路径和行号以 chip 展示。
- ASCII 架构图在浏览器中保持缩进、连线和横向滚动，不出现自动换行导致的错位。
- 长内容已折叠，首屏清爽。
- 长文档已加入左侧目录，目录链接能跳转到对应章节。
- 没有不必要的交互元素。
- 回复只说明文件路径和一句话概要。
