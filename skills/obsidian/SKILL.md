# Obsidian 笔记写作

把本 skill 当作写作编排器：先选择模式，再按需读取对应规则。不要把所有规则一次性加载，也不要让短笔记机械执行长文流程。

## 1. 确认 Vault 与局部约束

默认 Vault 为：

```plain
$HOME/Documents/Obsidian Vault/
```

用户给出其他 Vault 或目标文件时，以用户路径为准。写入前：

1. 确认目标目录存在。
2. 从 Vault 根目录到目标目录查找 `AGENTS.md`、`CLAUDE.md` 或其他局部规范；局部规范优先于本 skill。
3. 读取目标目录一篇同类型笔记，了解命名、双链、图片和章节粒度；用户指定参考文章时必须优先读取指定文章。
4. 修改旧文时先读完整原文和 front matter，不覆盖未知字段，不顺手清洗无关内容。

## 2. 选择写作模式

| 模式 | 适用任务 | 必要流程 |
| --- | --- | --- |
| 快速笔记 | 单个结论、命令、经验点、短会议结论 | brief-lite → 成稿 → 校验 |
| 技术笔记 | 机制解释、代码链路、方案分析、资料整理、问题复盘、完整指南 | 证据 → full brief → 大纲 → 成稿 → 分轮审校 |
| 公开文章 | `type: post`、博客长文、面向陌生读者的发布内容 | 研究 → full brief → 大纲 → 成稿 → 读者测试 → 发布门禁 |
| 旧文改写 | 补 front matter、局部重写、结构调整、更新事实 | 保留项 → 局部修改 → diff 审查 → 校验 |

选择后读取 [writing-modes.md](references/writing-modes.md)。工作模式决定流程和发布门槛，文档类型决定内容结构；两者分开判断。快速笔记对应快速记录；技术笔记和公开文章再选择教程、How-to、参考、原理说明、问题复盘或完整技术指南，不要用一套目录覆盖所有文档。

## 3. 建立写作合同

快速笔记只维护 brief-lite；技术笔记和公开文章维护 full brief。具体字段、判断—证据映射、style profile、knowledge map 和退出条件见 [content-brief.md](references/content-brief.md)。

写作合同至少要回答：

- 这篇笔记解决谁的什么问题。
- 读者读完应获得什么结论或能力。
- 哪些核心判断必须成立，各自依据是什么。
- 哪些内容明确不写，哪些事实仍不确定。
- 每个核心判断将落在哪个章节。

用户指定参考文章时，列提纲前必须形成 style profile，至少记录标题形式、章节展开顺序、段落密度、列表和表格、配图节奏、语气与叙述视角、可借鉴项和不可照搬项。没有完成 profile，不得开始大纲。

完整技术指南还必须形成 knowledge map：列出必须知识点、先决关系和唯一主章节。无法解释概念依赖、知识点存在遗漏或同一结论被分配到多个主章节时，不得开始正文。

full brief 是可检查的中间工件。长文可暂存为工作文件，短文可只在当前上下文中维护；除非用户要求记录写作过程，不把 brief、intake、内部评分写进最终笔记。

## 4. 先取证，再成稿

按以下优先级取证：

1. 技术实现：代码、提交记录、配置、日志、接口文档。
2. Vault 知识：已有笔记、真实双链、同目录约定。
3. 外部事实：官方文档、标准、项目 README、原始研究。
4. 用户素材：截图、链接、命令输出、草图和口述结论。

把素材整理为 evidence pack：事实、来源、可引用片段、时间或版本、待确认点、不能推断的内容。时间敏感事实必须核对日期；证据不足时降级措辞，不伪装成确定结论。

## 5. 生成结构与正文

1. 根据模式选用 [assets/templates](assets/templates) 中最接近的模板，只复制需要的部分。
2. 先写合法 front matter；字段规则见 [frontmatter.md](references/frontmatter.md)。
3. 大纲中的每个二级标题只承担一个解释任务，并覆盖至少一个 brief 核心判断或 knowledge map 知识点；标题必须准确命名对象、关系或机制。
4. 开头先给定位、结论、影响范围或适用边界，不用通用背景铺垫。
5. 段落负责解释判断，列表负责收束并列点、步骤和条件；代码、命令、字段和链路写到可复查。
6. 使用 [style-and-format.md](references/style-and-format.md) 完成 Obsidian 排版、双链和文末结构。
7. 只有图能明显降低理解成本时，才读取 [diagrams.md](references/diagrams.md) 并进入配图支线：技术流程、架构、状态和关系图调用 `svg-tech-diagram`；复杂概念示意、类比和封面调用 `generate-image`，由它选择 GPT Image 或 Banana 链路；UI、日志和运行结果使用真实截图证据。新图不使用 Mermaid、ASCII 或 `plain` 伪图。

## 6. 分轮审校

不要用一次“润色”同时解决所有问题。按 [quality-review.md](references/quality-review.md) 依次执行：

1. **合同覆盖**：核心判断、非目标和不确定项是否正确映射到正文。
2. **证据与准确性**：强判断是否有来源，代码和版本是否可复查。
3. **结构编辑轮**：检查参考风格对齐、概念依赖、专业标题、知识点遗漏与唯一主章节。
4. **文风编辑轮**：扫描全文和所有文字载体，处理口播表达、空转过渡、口号对比、同义反复和无依据评价。
5. **格式与发布**：front matter、标题层级、双链、附件和相关笔记是否正确。

结构编辑轮和文风编辑轮是技术笔记与公开文章的硬门槛；旧文反馈暴露系统性缺陷时，无论篇幅长短也必须执行。两轮不能合并成泛化“润色”，也不能只抽查正文段落。扫描范围包括标题、正文、表格、引用块、作者新增的代码注释以及 SVG 文字；逐字引用只标记问题并检查上下文，不擅自改写原文。

用户指出某一节的问题后，编辑范围仍保持必要最小，但审查范围必须扩展到全文和关联图示，查找同类缺陷。修复后重新执行结构轮、文风轮和自动校验，不能只复查被点名位置。

公开文章和较长技术笔记增加 reader test：让没有当前会话背景的新 Agent 只看正文，回答预期读者问题，并检查歧义、隐含前提和内部矛盾。reader test 只做一轮；新 Agent 不可用、调用失败或没有返回时，立即改做隔离式自测并说明限制，不无限等待。修复失败点后再交付。

## 7. 校验与交付

优先使用 Vault 自带校验入口；当前 Vault 若存在 `scripts/check-obsidian-vault.py`，按它的说明检查本次文件。没有项目校验器时，先把本 `SKILL.md` 所在目录解析为绝对路径 `SKILL_ROOT`，再运行 bundled validator；不要按当前 shell 工作目录猜测 `scripts/`：

```bash
python3 "$SKILL_ROOT/scripts/validate_note.py" --strict /absolute/path/to/note.md
```

交付前确认：

- front matter 与 `post` / `note` 发布形态匹配，没有占位值。
- 没有一级标题，正文从 `##` 开始。
- 关键判断均有证据、例子或明确的不确定性标记。
- 用户指定参考文章时，style profile 已完成且正文只借鉴结构规律，没有照搬措辞和判断。
- 完整技术指南的必须知识点覆盖完整，概念按依赖顺序出现，每个知识点只有一个主章节。
- 结构与文风两轮审查覆盖全文、表格、引用块、作者新增代码注释和 SVG 文字。
- 旧文修改保留了原有未知字段和未要求修改的内容。
- 本地图片链接全部有效，正文与图中术语不存在冲突。
- 文末包含 `---` 与 `## 相关笔记`，只链接真实存在或明确计划创建的笔记。
- validator 和 Vault hook 均通过。

最终只汇报目标文件、采用的模式、主要证据边界和校验结果，不暴露内部写作合同全文。
