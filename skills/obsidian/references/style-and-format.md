# 写作风格与 Obsidian 格式

## 写作风格

个人技术笔记优先追求信息密度、边界和可复查性，不写成营销文、百科词条或教程模板。完整技术指南优先采用专业参考文档结构，不强行加入个人化叙述。

- 开头先给定位、结论、影响范围、更新时间或适用边界。
- 一个段落只解释一个主要判断，通常 1 到 3 句。
- 段落用于解释，列表用于步骤、条件和并列项，表格用于稳定字段和方案比较。
- 把抽象判断改成具体对象、条件、例子或反例。
- 删除“总之”“值得注意的是”“从某种意义上”“核心在于”等没有新增信息的句子。
- 不为了形式完整添加历史、分类、FAQ、展望和重复总结。

## 专业标题

标题应准确命名本节讨论的对象、关系或机制。概念定义可以使用“什么是 X”，只有读者确实会自然提出的问题才使用问句；结构、原理、安全和排错章节优先使用名词性标题。

以下表达不是绝对禁词，但属于风险信号。出现时必须检查它是否提供了准确分类；如果只是为了显得轻松或制造悬念，就改成能直接命名内容的标题或句子：

- `先用一句话认识……`
- `先看……`
- `到底……`
- `真正好用的……`
- `……长什么样`
- `最重要的不是……而是……`
- `回到刚才的例子……`

同样检查没有必要的“你可以……”。能直接陈述条件、动作或结果时，不虚构对话感。标题不能只写“核心结论”“进一步思考”“几个问题”这类无法从目录判断内容的空壳名称，除非文档类型和上下文已经让对象唯一明确。

## 标题与空行

- 不写 `#` 一级标题，文件名承担一级标题角色。
- 大章节使用 `##`，子节使用 `###`，必要时再用 `####`。
- 标题后直接跟正文，不插入装饰性空行。
- 引用块和代码块前后保持紧凑。
- Markdown 表格前后保留一个必要空行，避免渲染为普通文本。
- `---` 水平分隔线前后保留空行，避免与 front matter 或正文混淆。

## 强调、引用与代码

- 关键词和重要概念用粗体，不连续加粗整段。
- 补充说明、限制和风险用引用块；警告可写 `> ⚠️`。
- 代码块必须声明语言，如 `kotlin`、`java`、`xml`、`bash`、`yaml`、`plain`。
- 命令、字段、文件名和配置值使用行内代码。

## 双链与附件

- 写入前搜索目标 Vault，优先链接真实存在的相关笔记。
- 使用 `[[笔记名]]`，需要显示别名时使用 `[[笔记名|显示文本]]`。
- 不为了凑数量编造双链；计划创建但尚不存在的笔记要明确说明。
- 图片和 SVG 优先放在当前主题目录的 `img/` 子目录。
- 使用 `![[img/example.svg|760]]` 这类相对路径，宽度按内容需要设置。

## 文末结构

正文用以下结构收尾：

```markdown

---
## 相关笔记
- [[真实存在的相关笔记]]
```

相关笔记之前不再添加空泛总结。没有可验证链接时保留章节，但不要虚构条目。
