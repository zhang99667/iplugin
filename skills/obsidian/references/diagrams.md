# 配图决策与工具路由

只有图能明显降低理解成本时才配图。先写 image brief，再调用具体绘图能力；不要看到“流程”“架构”就机械加图。

## Image brief

开始绘图前明确：

- 图要解决什么理解问题。
- 读者看完图必须获得什么结论。
- 必须出现的节点、方向、分组、状态或视觉对象。
- 哪些细节必须精确，哪些只承担概念表达。
- 输出文件名、目标 `img/` 目录和正文嵌入位置。

image brief 只约束信息和视觉目标，不预先写绘图实现细节。

## 三条配图路径

| 路径 | 适用内容 | 执行能力 | 交付形态 |
| --- | --- | --- | --- |
| SVG 技术图 | 流程、架构、时序、状态、依赖、数据流、对比矩阵、分层关系 | `svg-tech-diagram` | 独立 `.svg`，另保留审阅用 `.png` |
| 复杂概念图 | 抽象机制、场景化类比、复杂视觉示意、封面和记忆点 | `generate-image` | GPT Image 或 Banana 生成的最佳位图 |
| 真实截图 | UI 状态、日志、运行结果、配置界面和前后对比 | 当前环境的截图/设备/浏览器能力 | 原始证据图或必要标注后的图片 |

新图不使用 Mermaid、ASCII 或 `plain` 伪图。关系很简单时直接用正文、编号列表或表格；只要值得单独成图，就使用 SVG。

## SVG 技术图

SVG 是结构化技术配图的默认路径，简单流程和复杂架构都适用。调用 `svg-tech-diagram`，完整执行它的生产与自审链路：

```text
提炼信息结构
→ 选择布局并编写 SVG
→ 几何闸门
→ 渲染 PNG
→ 像素闸门
→ 实际查看预览
→ 修复后重新验证
```

要求：

- 箭头、节点、文案和正文术语一致。
- 图中文字只放关键词和短句，解释留给正文。
- `.svg` 放入当前主题 `img/`，使用相对 Obsidian embed。
- PNG 只用于视觉 QA；最终笔记优先引用 SVG，保证放大清晰和后续可编辑。

## GPT Image / Banana 图像生成

当图的价值来自复杂视觉构图、场景、类比或形象化解释，而不是精确节点与连线时，调用 `generate-image` skill，不在 Obsidian skill 内重复实现接口逻辑。

- 用户没有指定链路时，按 `generate-image` 默认 GPT Image 路由执行。
- 用户提到 Banana、Banana2 或 Gemini 兼容链路时，按 `generate-image` 的 Banana 路由执行。
- 遵循该 skill 的候选图策略、API key 处理和视觉筛选规则；通常并发生成候选，只保留最佳图。
- prompt 描述视觉目标，不把 `gptimage`、`banana` 等路由词写进画面需求。
- 生成后实际查看图片，检查主体完整度、错误文字、水印、技术事实和与 image brief 的一致性。

需要精确字段、文字、箭头或状态关系时不要使用图像生成，改用 SVG。

## 真实截图证据

截图不是装饰图，而是证据：

- 保留判断所需上下文，不把关键时间、状态、错误码或对照区域裁掉。
- 对账号、token、内部地址和个人信息做脱敏。
- 记录截图来源、环境、日期和必要操作条件。
- 标注只强调正文正在讨论的区域，不用大量箭头和色块遮住原始证据。
- UI 或运行状态能够直接截图证明时，优先截图，不重新画一张近似图。

## 正文承接与旧图处理

- 图前说明为什么需要看图，图后指出最重要的结论。
- 同一小节不连续堆表达相近的图。
- 生成或采集后确认文件存在、路径正确、在 Obsidian 中可渲染。
- 不批量迁移历史 Mermaid 图；修改旧文且本次需要调整该图时，再用 SVG 替换并检查正文引用。
